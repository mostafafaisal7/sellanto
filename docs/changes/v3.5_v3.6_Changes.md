## 1. v3.5 — `f3e248de` deep dive

### 1.1 Robust LLM JSON extraction

**File:** [accounts/services/llm_service.py](../../accounts/services/llm_service.py)

Three new pieces:

#### `_FENCE_RE`

```python
_FENCE_RE = re.compile(r'```(?:json)?\s*(.*?)\s*```', re.DOTALL | re.IGNORECASE)
```

Captures the contents of any `\`\`\`` / `\`\`\`json` fenced block, multiline, case-insensitive.

#### `_find_json_span(text) -> Optional[str]`

A balanced-span scanner. Walks the string, finds the first `{` or `[`, then tracks open/close depth — but with two refinements that the old `.split('\`\`\`')` logic missed:

- **String-literal awareness:** a `"` toggles `in_str`; while in a string, `{`, `}`, `[`, `]` are ignored. So a caption like `{"hook": "Don't forget the {flavor} secret"}` no longer confuses the parser.
- **Escape handling:** a `\` inside a string sets `escaped = True`, which then skips the next character. So `{"a": "He said \"hi\""}` still parses cleanly.

Returns the exact substring of the balanced span, or `None` if nothing balances.

#### `extract_json_object(text)`

The public helper. Three-stage fallthrough:

1. **Happy path:** `json.loads(text.strip())`. If the model returned pure JSON (which it usually does), zero overhead — no regex, no scan.
2. **Code fence:** `_FENCE_RE.search(...)`. If the model wrapped the payload in `\`\`\`json … \`\`\``, take the fence body and try `json.loads` on it.
3. **Balanced span scan:** if both fail, run `_find_json_span` on whatever's left to handle the "prose before, prose after, JSON in the middle" case.

If everything fails, raises `json.JSONDecodeError` so existing callers that already wrap `json.loads` in `try/except` keep working **without code change**. This is the key compatibility property — every call site can adopt `extract_json_object` by name swap alone.

#### Tests — [accounts/tests.py](../../accounts/tests.py)

A new `ExtractJsonObjectTests(SimpleTestCase)` class covers:

- Pure JSON
- `\`\`\`json` fences
- Plain `\`\`\`` fences
- Prose before the JSON
- Prose after the JSON
- Prose with embedded fence
- Braces in string values
- Top-level arrays (`[…]` not just `{…}`)
- Invalid input raises `json.JSONDecodeError`

#### Adoption — [api/views.py](../../api/views.py) and [api/strategy_views.py](../../api/strategy_views.py)

Every Brand DNA / insights / ideas parse site swapped from the previous hand-rolled `text.strip().lstrip('\`\`\`json').rstrip('\`\`\`').strip()` to `extract_json_object(...)`. Specifically:

- `GenerateBrandDNAView` — manual-website enhance path, live `web_search` flow, AI-enhance-brand path
- Insights endpoint in `strategy_views.py`
- Idea-generation endpoint in `strategy_views.py`

When parsing fails, the Brand DNA path now also emits **brand id + model `finish_reason` + truncated response excerpt** to the log, making prod regressions diagnosable without re-running the call.

### 1.2 BoomerangVideo on the landing page

**New file:** [frontend/src/components/landing/BoomerangVideo.tsx](../../frontend/src/components/landing/BoomerangVideo.tsx) (72 lines)

The component plays a ping-pong loop: forward → reverse → forward, forever. Two browser constraints shape the implementation:

- `<video loop>` only loops forward. There's no native "boomerang" attribute.
- `playbackRate = -1` is **not supported in Chrome** (it's a WebKit-only behavior). So you can't just flip the rate to reverse.

The component solves it by:

1. Letting the video play forward naturally until `'ended'` fires.
2. On `ended`, pausing the video and starting a `requestAnimationFrame` loop that **decrements `currentTime`** by the frame delta each tick.
3. When `currentTime` reaches `0`, calling `v.play()` to resume forward playback.
4. `muted` + `autoPlay` + `playsInline` so every browser allows autoplay.

The frame-delta trick keeps reverse playback frame-rate-independent — on a 144 Hz monitor it still takes the same wall-clock time as the forward pass.

**Mounted in:** [frontend/src/components/landing/AIVideoSection.tsx](../../frontend/src/components/landing/AIVideoSection.tsx)

The static gradient placeholder + centered play-icon were removed; `<BoomerangVideo src="/medias/videos/9dd17588-….mp4" />` replaces them. Visitors land on a real generated clip instead of a "coming soon" tile.

```python

    …

        self.media_files = json.dumps(files)

class MagicModeCache(models.Model):
```

The `Post`-shaped helpers were indented inside `MagicModeCache` (Python doesn't reject this — it just attaches them to the wrong class). The stray `media_files_list` property and `set_media_files` duplicate (which referenced fields the cache model never had) are gone.

This is a silent functional restoration — every view, signal, and task that called `post.mark_as_posted()` or `post.can_be_cancelled()` was previously raising `AttributeError`. Worth a manual smoke-test on the scheduling and post-status paths after deploy.

## 2. v3.6 — `f92ad7fd` deep dive

### 2.1 Attach generated media by reference — the headline fix

**The bug:** Magic Mode generates images and videos server-side first, then the frontend tries to attach them to a post draft. The flow used to be:

```
backend → image URL → React fetch(URL) → Blob → File → FormData → POST /api/posts/
```

That browser `fetch()` was failing silently:
- Cross-origin URLs without CORS headers throw network errors before the image bytes arrive.
- Even when the fetch succeeded, the resulting `File` had no `lastModified`, mismatched MIME, etc.
- The `media_files` *string* parameter the React code was also sending in the same payload was **ignored** by the backend.

End result: caption present, media field empty.

**The fix:** accept generated media **by reference** server-side.

#### New helper — `_resolve_owned_media_paths(user, raw_paths, video_generation_id=None)`

**File:** [api/views.py](../../api/views.py)

Takes:
- A list of `/media/`-relative paths OR absolute media URLs
- An optional `video_generation_id` (for the video flow which knows the gen ID but not the final URL up-front)

Returns: a list of `MEDIA_ROOT`-relative paths that the user **provably owns**, suitable for assignment to `Post.media_files`.

The safety machinery:

```python
def _normalize(raw):
    rel = raw.strip()
    if rel.startswith('http://') or rel.startswith('https://'):
        rel = urlparse(rel).path                  # strip scheme+host
    rel = unquote(rel).replace('\\', '/')         # %20 → space, \ → /
    if media_url and rel.startswith(media_url):
        rel = rel[len(media_url):]                # /media/foo → foo
    rel = rel.lstrip('/')
    if not rel or '..' in rel.split('/') or ':' in rel:
        return None                                # traversal / drive qualifier
    full = os.path.realpath(os.path.join(media_root, rel))
    if full != media_root and not full.startswith(media_root + os.sep):
        return None                                # symlink-escape
    return rel
```

Then a **two-tier ownership check**:

1. **Subtree match:** if the relative path begins with `generated_images/{user.id}/`, `generated_videos/{user.id}/`, `video_thumbnails/{user.id}/`, or `posts/{user.id}/`, accept. These prefixes are guaranteed by the `upload_to` helpers in `ai_image` and `ai_video`.
2. **Exact field fallback:** if subtree didn't match, look up an `ImageGeneration` or `VideoGeneration` row for this user whose `generated_image` / `generated_image_with_logo` / `composited_image` / `generated_video` / `generated_video_with_logo` / `thumbnail` field equals the relative path. Useful for the copy-overlay variants whose path doesn't always begin with the standard prefix.

If neither path holds, the reference is **silently dropped**. A bad reference can never raise — draft creation always succeeds.

The optional `video_generation_id` branch fetches the `VideoGeneration` row, prefers `get_display_video().name`, falls back to `generated_video_with_logo.name` or `generated_video.name`. Same silent-drop semantics.

#### Wire-in — `PostViewSet.create`

After processing in-browser uploads, `PostViewSet.create` now does:

```python
media_paths_raw = request.data.get('media_paths')
if isinstance(media_paths_raw, str):
    try:
        parsed = json.loads(media_paths_raw)
        media_paths_raw = parsed if isinstance(parsed, list) else [parsed]
    except (json.JSONDecodeError, TypeError):
        media_paths_raw = [media_paths_raw]
elif not isinstance(media_paths_raw, (list, tuple)):
    media_paths_raw = [] if media_paths_raw is None else [media_paths_raw]

for rel in _resolve_owned_media_paths(
    request.user, media_paths_raw, request.data.get('video_generation_id')
):
    if rel not in media_files:
        media_files.append(rel)
```

`media_paths` accepts a JSON string, a list, a single string, or `null`. The result is **merged with**, not replaced by, the in-browser uploads — so callers can mix in-browser uploads with already-generated assets in the same draft request.

### 2.2 Brand-aware video captions

**The bug:** Captions for AI-generated videos were generated from the raw seed topic only. Result: captions described the video literally ("a person walks through a forest") instead of speaking in the brand's voice with a CTA appropriate to the platform.

**The fix:** route the same brand DNA + idea + trending + actual-video-prompt context that the visual prompt builder consumes into the caption generator.

#### New helper — `_build_caption_brand_context(...)`

**File:** [api/views.py](../../api/views.py)

Assembles four XML-block sections from the user's brand row + the caller's `idea` / `trending_topics` / `video_prompt`:

```
<brand>
  name: …
  voice: …
  values: …
  audience: …
  cta_style: …
</brand>

<creative_idea>
  title: …
  hook: …
  angle: …
</creative_idea>

<trending_themes>
  …
</trending_themes>

<video_prompt>
  …(truncated to 1200 chars)
</video_prompt>
```

Prefixed with a directive line:

> "Use the brand identity, creative idea and the video described below so the caption matches the actual video and the brand's voice (do NOT just describe the video):"

If all four are empty, returns `''` (no-op).

#### Wire-in — `generate_caption` endpoint

Parses `brand_id`, `idea`, `trending_topics`, `video_prompt` off the request and appends the assembled block to `custom_instructions`. The caption service signature stays the same — only the content of `custom_instructions` changes.

`idea` and `trending_topics` accept JSON-string variants as well as native lists/dicts.

#### Caption system-prompt promotion — [ai_caption/openai_service.py](../../ai_caption/openai_service.py)

The biggest leverage point: previously, `custom_instructions` was echoed in the **user** prompt. The LLM treated it as a suggestion and frequently ignored it for shorter / catchier output. Now, when `custom_instructions` is non-empty, `_build_system_prompt` appends:

```
<brand_context>
…the context block from _build_caption_brand_context…
</brand_context>
The brand_context above is a NON-NEGOTIABLE, high-priority constraint.
The caption MUST reflect this brand voice, creative idea, and the
described video/subject. Do NOT merely describe the video — write a
native social post that matches it and the brand.
```

Moving the constraint into the system prompt + framing it as "non-negotiable" empirically beat ~80% of the "caption describes the video" failure mode in informal testing.

#### Frontend consumers

**[frontend/src/services/captionService.ts](../../frontend/src/services/captionService.ts)** — `generate(...)` accepts `brand_id`, `idea`, `trending_topics`, `video_prompt`.

**[frontend/src/pages/magic/VideoWorkingScreen.tsx](../../frontend/src/pages/magic/VideoWorkingScreen.tsx)** — persists `brandId`, `firstIdea`, `trendingTopics` onto the `videoResult` store along with `videoPrompt` so the result screen can render the same context downstream without a second backend round-trip.

**[frontend/src/store/magicModeStore.ts](../../frontend/src/store/magicModeStore.ts)** — `videoResult` gains `videoPrompt`, `brandId`, `idea`, `trendingTopics`.

### 2.3 Draft preview modal

**[frontend/src/pages/DraftPostsPage.tsx](../../frontend/src/pages/DraftPostsPage.tsx)** and **[frontend/src/pages/magic/MagicDraftPage.tsx](../../frontend/src/pages/magic/MagicDraftPage.tsx)**

A new **View** modal launches in-page (no navigation). Contents:

- Status / schedule chip (`Draft`, `Scheduled for 3 Jun, 14:00`, etc.)
- Full caption (whitespace preserved)
- Large media — auto-detected image vs. video

#### `isVideoUrl(url)` detection

Used both by the thumbnail row and the preview modal:

- Splits off query string and hash so `?cache=123` doesn't fool extension match
- Returns `true` for `.mp4`, `.webm`, `.mov`, `.ogg`, `.m4v` (lower-cased)
- Renders `<video preload="metadata" controls>` for matches; `<img>` otherwise

Previously, the listing row rendered every draft as `<img>`. For video drafts that meant a broken-image icon. After this change, video drafts get a proper player.

#### Resume-in-Magic-Link removal

The old "Resume in Magic Link" / "Resume in Overflow" CTAs are removed from both pages — they pointed at flows that no longer exist after the v3.x consolidation. View modal is the replacement entry point.

### 2.4 Windows path normalisation

**[api/views.py](../../api/views.py)** `PostViewSet.create` — when writing uploaded media to disk:

```python
# was:
media_files.append(file_path)

# now:
media_files.append(file_path.replace('\\', '/'))
```

On Windows, `os.path.join('posts/123', 'image.png')` returns `'posts/123\\image.png'`. Persisting that into the JSON-encoded `media_files` field meant the browser tried to load `https://.../media/posts/123\image.png`, which 404s. Forward-slash normalisation fixes it for any Windows-hosted environment (CI, local dev, the team member running Windows).

This is independent of the by-reference work (§2.1) — uploads via the regular file-input path benefit too.

## 4. Risks / things to watch

1. **Path-safety surface in `_resolve_owned_media_paths`.** The function is the trust boundary between a user-supplied URL and `Post.media_files`. The safety checks (traversal, drive qualifier, realpath under `media_root`, subtree match) look correct, but this is a security-sensitive helper — worth a manual review on the next security pass.
2. **Caption system prompt now larger.** Adding the `<brand_context>` block bloats the system prompt by ~600–1200 chars per call. Token cost on a 4o-mini caption is still negligible; on Claude with extended thinking this matters more.
3. **Boomerang video is ~6.6 MB.** First-paint cost on the landing page goes up. Confirm this is acceptable for the mobile audience or gate the autoplay behind `prefers-reduced-motion: no-preference`.
4. **`MagicModeCache` reshape is a migration-free model change.** Nothing in the DB schema changed (the field set wasn't actually different), but if you have ORM-level queries that used the (broken) `MagicModeCache.media_files_list` property, they'd silently 500. Grep should turn up zero hits, but worth confirming.
5. **Silent-drop semantics on `_resolve_owned_media_paths`.** Means a frontend bug that passes a *wrong* URL won't surface as an error — it'll create a draft with no media. The flip side of robustness. Log an info-level line on every dropped reference if production diagnostics ever need it.
6. **The `looksDescriptive` regex removal** in `VideoResultScreen.tsx` means a very short, low-quality caption from the LLM will now be accepted as-is instead of triggering the local fallback. Acceptable trade-off (the regex was a noisy false-positive), but watch for user reports of one-line captions.
