## 1. AI Cost Audit + Admin Cost-Tuning UI

### Problem
`DIAMOND_COSTS` was a hard-coded Python dict — every price change needed a deploy. Initial inspection vs the rate tables in `cost_calculator.py` showed most features priced 78–94% below the documented "3× SaaS markup" target. A 5-second Veo 3.1 video costs $2.00 raw but charged only 500 💎 (= $0.50 cost-basis).

### Headline finding
At the 3× markup target, current diamond costs were under-priced across the board:

| Feature | Real $/call | Currently | Target 3× | Gap |
|---|---|---|---|---|
| `video_5s` | $2.00 | 500 💎 | **6,000 💎** | −92% |
| `image_standard` | $0.067 | 15 💎 | **201 💎** | −93% |
| `brand_dna` | $0.039 | 15 💎 | **117 💎** | −87% |
| `caption` | $0.018 | 5 💎 | **54 💎** | −91% |
| `support_chat` | $0.0105 | 2 💎 | **32 💎** | −94% |

A typical `/overflow` run (3 competitors, 5 ideas, 5 captions, 5 images, no video) was deducting **187 💎** when the 3× target would be **2,059 💎** — roughly 11× under-charging.

- **Migration [accounts/migrations/0024_featurecostconfig.py](accounts/migrations/0024_featurecostconfig.py)** — creates the table and seeds 40 rows from the current `DIAMOND_COSTS` dict so day-1 behaviour is unchanged.

- **Added [accounts/services/cost_calculator.py](accounts/services/cost_calculator.py):** new `FEATURE_TYPICAL_TOKENS` dict (per-feature input/output token volumes) + `estimate_feature_raw_cost_usd()` helper that routes through the existing `calculate_text_cost / calculate_image_cost / calculate_video_cost / calculate_voice_cost` helpers.

## 2. Historical reconciliation — drive prices from real DB data

### Problem
Phase 1 priced features against **theoretical** token volumes from `FEATURE_TYPICAL_TOKENS`. Real usage may differ. We have months of `DiamondTransaction` rows recording exact `input_tokens / output_tokens / model_used / duration_seconds / media_count` per call — those should drive the recommendations.

### What the real data showed
Aggregating last 30 days of `DiamondTransaction` deductions:

| Feature | Calls | Real avg $/call | Currently | History-grounded recommendation |
|---|---|---|---|---|
| `image` | 34 | $0.063 | 15 💎 | **189 💎** |
| `brand_dna` | 23 | $0.029 | 15 💎 | **88 💎** |
| `competitor_analysis` | 7 | $0.045 | 12 💎 | **135 💎** |
| `strategy_ideas` | 33 | $0.011 | 10 💎 | **33 💎** |
| `caption` | 48 | $0.008 | 5 💎 | **24 💎** |

**Key insight vs the theoretical audit:** `caption` real avg is $0.008/call, not the $0.018 estimated in the audit doc. Users send shorter prompts than upper-bound estimates assumed. Real target is 24 💎, not 54 💎.

Total over 30 days: 187 calls, $3.87 real API cost, 7,931 💎 charged (= $7.93 cost-basis) → net margin **+$4.07** (≈2× cost, just under the 3× target).

### Backend
- **New service** [accounts/services/feature_cost_recommender.py](accounts/services/feature_cost_recommender.py):
  - `aggregate_historical_costs(lookback_days, category)` — full per-feature aggregation with provider mix, margin, recommended_flat_override
  - `recommend_price(feature, lookback_days)` — single-feature recommendation, falls back to typical-token estimate when < 5 historical calls
  - `apply_recommendations(features, lookback_days, actor)` — bulk-applies `flat_override_diamonds`, records `actor` in `updated_by`, skips low-confidence features, writes audit trail to `notes`
- **3 new admin endpoints** in [api/admin_views.py](api/admin_views.py):
  - `GET /api/v1/admin/feature-costs/history/?days=30&category=text`
  - `POST /api/v1/admin/feature-costs/<feature>/recommend-from-history/`
  - `POST /api/v1/admin/feature-costs/apply-recommendations/`
- **URLs wired carefully** in [api/urls.py](api/urls.py) — static suffixes (`history/`, `apply-recommendations/`, `<feature>/recommend-from-history/`) listed **before** the `<str:feature>/` catch-all so Django doesn't route `/history/` into `AdminFeatureCostDetailView`.

## 3. Bug fix — Days Remaining card showing `∞`

### Reported
`/analytics/diamond` page showed "**∞d** / No usage in last 14d" for `admin123` even though the wallet had 14,788 💎 balance, 262 💎 lifetime spent, and 187 calls recorded historically.

### Root cause
[api/diamond_views.py:269](api/diamond_views.py#L269) `DiamondForecastView` filtered deductions to the last 14 days only. Admin had no usage in that window → `avg_daily = 0` → `days_remaining = None` → frontend showed `∞`. Mathematically correct, practically useless.

### Fix
Updated `DiamondForecastView` to use a tiered resolution:
1. **Try requested window** (default 14d).
2. **Auto-expand** to 30 → 60 → 90 days if empty.
3. **Fall back to lifetime average** (`total_spent / days_since_first_deduction`) if still empty.
4. **Return `null`** only when there's genuinely zero usage ever recorded.

Two new response fields:
- `effective_lookback_days` — the window that actually drove the calc.
- `fallback_used` — `''` | `'expanded_window'` | `'lifetime_average'`.

Frontend ([DiamondAnalyticsPage.tsx:371](frontend/src/pages/DiamondAnalyticsPage.tsx#L371)) subtitle now reads "Empty by Aug 25, 2035 · last 60d avg" so the user can see both the runway and which window drove the estimate.

### Result for admin123
**Before:** `∞d` / "No usage in last 14d"
**After:** `3,386d` / "Empty by Aug 25, 2035 · last 60d avg"

Endpoint returns: `balance=14,788`, `effective_lookback_days=60`, `spent_in_window=262`, `avg_daily_spend=4.37`, `days_remaining=3386.6`, `fallback_used='expanded_window'`.
